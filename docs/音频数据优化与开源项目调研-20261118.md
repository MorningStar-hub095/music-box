# 音频数据优化方案分析 & GitHub 同类开源项目调研（2026-11-18）

> 性质：思路与分析（不含代码）。数据依据：本项目 2026-11-17 核查实测结果 + 2026-11-18 本机网络可达性实测 + 开源项目公开资料检索核实。
> 可达性实测环境：本机（中国网络），curl 计时，2026-11-18。

---

## 一、问题定位：为什么"有效音频数据不理想"

清理后现状：曲库有效口径 506 首，全部依赖本地缓存文件（4.2GB，条条可播）；远程直链有效率 0；打包端 URL 刷新链路不可用（无 tools 目录 + Python 依赖缺失）。

根因链（每一环都实测确认）：
1. **来源模式错误**：曲库 100% 来自爬虫抓取的"时效签名直链"——这类链接设计上就短寿命（实测 825 条全部 403，签名日期段 2026-07/08），把临时链接当持久数据存库，注定持续腐烂。
2. **刷新机制依赖未授权爬虫**：`refresh_song_url.py` 走网易云接口逆向，桌面端未随包分发，开发机缺 `pycryptodome` 也跑不通——刷新链路形同虚设。
3. **音频资产不可分发**：真实可播的 4.2GB 缓存不能进安装包（首装 pgdata.zip 仅含数据库），换机器/新装用户拿到的是"有目录无音频"的空壳曲库。
4. **播放体验建立在缓存存量上**：缓存是消耗性资产（LRU 淘汰 + 换机清零），没有可持续的补充来源。

**本质结论：需要把"音频数据来源"从『爬取平台临时链接』切换为『可持续、可授权、可分发的供给体系』，同时保留现有缓存代理架构作为统一服务层。**

### 2.2 桌面端 vs 网页端的关键差异

- **桌面端**：可全量本地化（内置/预下载），断网演示是硬需求 → A1/A2 是唯一能保证"离线 100% 可播"的路线；B1/B2 只能作为联网补充。
- **网页端**：永远依赖服务端代理（现有 `/api/audio/{trackId}` 缓存代理链路完全可复用），差异只在代理上游是谁（CDN / Jamendo / 本地文件）——架构上是"换上游"而非"改前端"。
- 两端统一约束：HTTP Range 拖动播放、CORS、Content-Type 正确性（现有服务端已实现，直接受益）。

## 三、GitHub 同类开源项目调研（按项目整理）

> 标注【已核实】= 本次检索/实测确认；其余为项目公开资料的通行认知，落地前建议再核对一次官方仓库。

### 3.1 MTG-Jamendo Dataset（`mtg/mtg-jamendo-dataset`）——公开数据集路线的标杆【已核实】

- **数据来源**：Jamendo 平台 CC 授权曲目，55,000+ 完整音频（320kbps MP3）+ 195 个标签（genre 87 / instrument 40 / mood-theme 56）。
- **获取方式**：MTG UPF 官方托管 TAR 分包 + Google Drive 镜像 + 校验脚本；另提供预计算 mel-spectrogram（NPY）与 Essentia 统计特征（JSON）。
- **质量筛选标准**（可直接借鉴的管线）：时长过滤（>30s，56,639→55,701）→ 标签清洗合并（tag_map）→ 冷门过滤（标签至少 50 个不同艺术家，→55,609）→ 按任务切分（genre/instrument/moodtheme/top50 子集）。
- **预处理流程**：统一 320kbps MP3 重编码；特征预计算随数据集分发——**这一点对本项目价值极大**：本项目 song_genres/moods/scenes 标签稀疏（清理后 genres 20 / moods 3 / scenes 5），MTG-Jamendo 的 195 标签可直接映射进 song_genres/song_moods 表，一步补齐推荐模块最缺的语义标签。
- **授权与合规**：音频逐曲 CC（曲面上各不相同，需逐曲登记）；元数据 CC BY-NC-SA 4.0，官方声明**仅限非商业研究/学术用途**，商用需联系 Jamendo S.A. 授权（2026 年 Jamendo 诉 Suno 案卷证实了这一限制的实际执行力）。本项目为课程/学习演示属非商业，可用；任何商用化前必须切换授权。
- **适用条件**：需要"质量高、标签全、授权可查"的批量曲库补充时首选；不适合当"主流华语热门曲库"（内容以欧美独立音乐为主，与现有 506 首华语曲库重叠度低——但这反而是扩库优势）。
- **潜在风险**：体量（全量 508GB，必须子集化，如 moodtheme 子集 152GB 仍太大，实际应按标签抽 500~2000 首）；海外下载速度（需评估分批拉取耗时）。

### 3.2 YesPlayMusic / R3PLAYX（`Sherlockouo/music` 等）——平台 API 代理路线的反面教材【已核实】

- **数据来源**：Binaryify/NeteaseCloudMusicApi 非官方逆向 API（3 万 star）。
- **结局**：2024-01 网易发法务函（明确援引《著作权法》《刑法》条款，指控"破解绕开限制、非法攫取流量"），作者清空全部代码并声明"保护版权，此仓库不再维护"；衍生项目只能自带分叉的 API 代码并在 README 声明"仅供个人学习研究、禁止商用"。
- **与本项目的关系**：本项目的爬虫 + 时效直链路径与此完全同构——链接 100% 失效只是这条路的第一个死法，法律风险是第二个。**结论：不作为数据来源，仅作为"降级兼容层"保留代码路径（默认关闭，供课程演示"为什么不行"）。**

### 3.3 落雪/洛雪音乐（lx-music）——音源解耦路线【已核实】

- **数据来源**：软件本身**零音源**——内置音源接口已全面失效（社区文档原话："内置的音乐接口全部失效，导致洛雪音乐成为一个本地音乐器"），播放完全依赖用户自行导入的第三方"自定义音源" JS 脚本解析各平台。
- **获取方式**：脚本由用户导入（在线地址或本地文件），软件把"搜索/取播放链接"抽象为脚本协议。
- **质量筛选/预处理**：无（音源质量完全取决于第三方脚本，链接失效是社区常态，"换源/重启"是标准排障动作）。
- **授权与合规**：Apache-2.0 开源 + 免责声明（"数据来自各平台公开服务器…版权数据请 24 小时内清除"）。本质是**风险转移而非消除**——平台方打击对象历来是音源脚本而非播放器壳，但这不是可依赖的护城河。
- **借鉴点**：① "播放器内核与音源供给解耦"的架构思想值得抄——把音乐盒的音频来源抽象为可插拔 Source（内置库/自托管/API），换源不动架构；② 反面教训：解析型音源无稳定性可言，别把曲库可用性押在任何第三方解析上。

### 3.4 Navidrome / Airsonic（+ beets）——自托管自有曲库路线

- **数据来源**：用户自己的音频文件，服务端只做索引与流式播放（Subsonic API 协议）。
- **获取方式**：用户放入音乐目录 → 自动扫描建库。
- **质量筛选/预处理（beets）**：去重（acoustic fingerprint）、时长/码率校验、标签规范化、封面/歌词自动补全、按元数据整理目录——这一套清单可直接移植为本项目"导入 local-music 时的入库校验管线"。
- **授权合规**：**零风险**（内容全归用户所有），这也是它是唯一被广泛商用部署的开源音乐方案路线的原因。
- **借鉴点**：① Subsonic API 兼容——若音乐盒实现/对接该协议，可直接消费用户已有音乐库生态；② 入库校验管线与本项目 audio-cache 的魔数/时长校验思路同源，扩展为"local-music 导入规范"即可。

### 3.5 spotDL / Spotube——第三方公开流匹配路线（风险案例）

- **数据来源**：Spotify/YouTube Music 元数据 + yt-dlp 抓取 YouTube 音频流，按 ISRC/标题匹配。
- **合规**：违反 YouTube ToS 的下载条款，灰色；且 YouTube 在中国大陆不可直连。**本项目不推荐**，列出仅为完整性——它证明"元数据一处、音频另一处"的匹配模式技术上成熟，若未来对接合法音源（如自托管库）可复用该匹配思想。

### 3.6 ListenBrainz / MusicBrainz——元数据补充（无音频）

- **数据来源**：社区维护的开源音乐元数据库（CC0 为主：曲目/艺术家/关系/标签），ListenBrainz 提供真实收听数据。
- **借鉴点**：本项目"时长缺失/标签稀疏"的元数据修复可对接其开源 API 做 ID 匹配补全；无音频版权问题，可放心用于元数据层。

## 四、把现有音频改为"线上数据"的可行方案

现有可复用资产：`/api/audio/{trackId}` 内存→磁盘→上游三级代理、磁盘 LRU、url-manager 调度骨架、`local-music` 目录与演示模式机制。以下方案都是"换上游/加上游"，不动播放链路。

### 方案 A：内置合规曲库（local-music 打包进安装包）

- **做法**：挑选 100~200 首高质量曲目（自有/CC0/CC-BY，优先中文独立音乐人授权或 MTG-Jamendo 子集），统一 128~192kbps MP3（控制包体在 400~600MB），随安装包分发，入库时写 `data_source=manual` + 逐曲授权记录。
- **适用场景**：课程答辩、离线演示、首次开箱体验。
- **关键约束**：安装包体积上限（现 pgdata.zip 21MB → 音频会显著增大包体，可拆"基础包+可选曲库包"）；逐曲授权登记与归属展示（CC-BY 义务）；选曲要覆盖多风格以保证推荐演示的区分度。
- **评估**：有效性/稳定性/延迟最优、合规零风险、成本一次性；缺点是曲库规模封顶。

### 方案 B：自托管授权内容源（对象存储 + CDN）★ 主推

- **做法**：把 CC 授权曲目（MTG-Jamendo 子集 + Jamendo 官方下载 + Pixabay 等人工筛选）预处理后（统一码率、魔数/时长校验、补标签）上传至国内对象存储并挂 CDN，服务端 audio 代理的上游从"网易直链"换成自有 CDN 地址；`audio_url` 字段重新启用，url-manager 调度器变为对自有源的定期健康检查（从此检查的是自己的源）。
- **适用场景**：日常使用与规模化扩库（500~2000 首），桌面端与网页端同源。
- **关键约束**：存储/流量成本（128kbps ≈ 1MB/分钟，1000 首 × 4 分钟 ≈ 4GB 存储，播放流量按月几十 GB，费用低）；必须保留逐曲 license 清单（来源 URL、CC 类型、登记日期）；CDN 引入国内域名备案问题（或用免备案对象存储直链，延迟略高）。
- **评估**：稳定性与延迟接近本地、规模可扩展、合规清晰——是"线上数据"的正解。

### 方案 C：在线授权 API 实时接入（Jamendo 为主、Audius 为辅）

- **做法**：服务端新增 source-adapter，搜索/补库时调 Jamendo API（注册 client_id，官方授权 CC 流媒体），音频经现有代理 + 磁盘缓存落地；Audius 作为长尾补充池（API 实测可达）。
- **适用场景**：联网环境下曲库无限扩展、新内容持续补充；演示"实时获取"能力。
- **关键约束**：海外源延迟（本机实测 API 1.5~1.7s，媒体流首包需实测，建议"先缓存后播放"策略兜底）；Jamendo 商用需签授权协议（非商业演示可用）； Audius 内容质量参差需二次筛选；**必须继承现有"试听片段检测"校验**（时长偏差检测），杜绝把片段当完整音频入库——这是本项目已立的红线。
- **评估**：接入成本最低的"在线实时"路线，稳定性受制于海外网络，适合做补充而非基座。

### 推荐组合：**A + B 打底，C 做增量**（三层供给）

```
首开箱：内置 100~200 首（A）           → 离线可演示，零依赖
日常库：自托管 CDN 500~2000 首（B）    → 稳定、合规、可扩展
长尾增量：Jamendo/Audius 实时接入（C） → 联网扩库，缓存落地
遗留路径：网易爬取（默认禁用）          → 仅保留"为什么不行"的教学演示价值
```

**不推荐**：继续以平台爬取为主数据源（稳定性实测归零 + YesPlayMusic 法律先例）；Spotify/Deezer 30s 试听（违反"完整音频"红线）；Internet Archive/Musopen 作主源（本机实测不可达/Bot 拦截）。

## 五、需要验证的指标（落地验收清单）

| 维度 | 指标 | 建议标准 |
|---|---|---|
| 时效性 | 首播延迟 P50/P95（缓存未命中→出声，桌面+网页分开测） | P95 < 2s（自托管）/ < 4s（Jamendo 实时） |

| 网络适配 | 各候选源 7 日多时段连通率与 RTT（重点：Jamendo 媒体 CDN、自有 CDN、Audius 节点） | 主源 ≥98% |

| 成本 | 存储（GB）/ 月流量（GB）/ 费用 | 1000 首约 4~8GB 存储，流量按实际用户量估算 |
| 合规 | 逐曲 license 登记覆盖率、归属信息展示（CC-BY 义务）、非商业使用声明 | 100% / 100% / 100% |

**首个验证动作建议**：先花半天做一次 Jamendo API + 自托管 CDN 的端到端 POC（取 20 首 → 预处理 → 上传 → 走现有代理播放 → 采集首播延迟/seek/完成率），用实测数据再定 B 与 C 的配比。
