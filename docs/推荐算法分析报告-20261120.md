## 一、整体架构与核心流程

### 1.1 架构总览

推荐系统采用**「多路召回评分 → 加权融合 → MMR 多样性重排 → Top-K 持久化」**的混合推荐架构，由 8 个子模块组成：

```
GET /api/recommendation/daily (recommendation.routes.ts:9)
  └→ RecommendationController.daily (recommendation.controller.ts:8-29)
      └→ RecommendationService.generateForUser (recommendation.service.ts:44-138)
          ├─① 数据采集（并行 5 查）       → Prisma：listening_event / recommendation_feedback / daily_recommendations
          ├─② 画像构建 UserProfile        → user-profile-builder.ts
          ├─③ 行为分析 BehaviorInsight    → behavior-analyzer.ts
          ├─④ 候选池 CandidatePool        → recommendation.service.ts:140-171（Redis 300s 缓存）
          ├─⑤ 四路评分
          │    ├─ RuleEngine              → rule-engine.ts（规则：风格/情绪/热度/时段/新鲜度/趋势/跳过惩罚）
          │    ├─ ContentFilter           → content-filter.ts（特征质心余弦相似度）
          │    ├─ CollaborativeFilter     → collaborative-filter.ts（用户 Jaccard 相似度 + 协同评分）
          │    └─ AIEnhancer.score        → ai-enhancer.ts（确定性启发式，非 LLM）
          ├─⑥ RecommendationFusion.fuse   → recommendation-fusion.ts（动态加权求和 + 收藏加分）
          ├─⑦ MMR 多样性重排              → preference.engine.ts:mmrSelectBySimilarity
          └─⑧ Top-10 持久化              → daily_recommendations 表（recommendation.service.ts:215-228）
```

**附属推荐链路**：
- **相似歌曲**：`GET /similar/:songId` → SimilarSongRecommender（similar-song-recommender.ts，特征向量 0.6 声学 + 0.4 语义相似度，Redis 30min 缓存）
- **基因图谱**：genome.service.ts —— 对 8 维声学特征做 PCA 降维（power iteration 自实现，genome.service.ts:27-72），每日定时重算（scheduler.ts:170-178），最近邻用参数化 SQL（genome.service.ts:146-155）
- **电台个性化**：radio-stream.service.ts:201-215 以 **3 秒超时竞速**调用 `generateForUser`
- **定时任务**：scheduler.ts —— 爬取后清候选池缓存（112-121）、每日 PCA 重算（170-178）、遍历活跃用户预生成每日推荐（281-285）

### 1.2 核心流程要点（generateForUser，recommendation.service.ts:44-138）

1. **采集**（49-72 行）：最近 50 条播放事件（`config.windows.recentPlays`）、30 天内反馈、30 天内播放、30 天内已推荐歌曲、全部收藏事件
2. **排除集**（74-79 行）：最近播放 ∪ dislike ∪ 30 天内已推荐 —— 保证每日推荐不重复
3. **冷启动分流**（85-87 行）：无播放事件 → 直接 `fallbackHot`（按 hotScore 排序取 10 首）
4. **候选池**（95-96, 140-171 行）：`playable && !archived && audioUrl≠''` → take 2000 → `isMusicContent` 关键词/时长过滤（176-209 行，排除播客/有声书/白噪音，标题编号格式，时长 <30s 或 >600s）→ 有特征优先排序 → 截取 1000，Redis 缓存 300s
5. **融合评分**（111 行）→ **MMR 全序重排** → **Top-10**（117 行）→ 不足时 fallbackHot 补齐（125-132 行）→ 持久化当日去重后重建（215-228 行）

## 三、权重与参数设置及合理性分析

### 3.1 混合权重（config.ts:36-42）

| 权重 | 默认值 | 依据与评价 |
|---|---|---|
| rule | 0.30 | 规则可解释、冷启动可用，占最大权重合理 |
| content | 0.30 | 与 rule 并列。**但见 5.1：声学特征全 0.5，实际判别力打折** |
| collaborative | 0.25 | **存疑**：桌面单用户场景相似用户几乎恒为空，恒返默认分 0.3（collaborative-filter.ts:30），0.25 权重成为常量项，实际效果是给所有候选统一加 0.075——不影响排序只影响分数均值 |
| ai | 0.15 | 名为 AI 实为第二组风格/情绪匹配（ai-enhancer.ts:92-116），**与 rule 的风格 0.3+情绪 0.25 信号重复**，等效风格权重膨胀至约 0.375 |

**动态权重**（config.ts:94-122）方向正确：冷启动（事件<10）降协同 0.05 升内容 0.15；负反馈率>50% 降 AI 升内容；归一化。但**协同权重没有覆盖"单用户且相似用户为空"这一实际常态**。

### 3.2 MMR λ=0.7（config.ts:43-45）

fusion 注释（recommendation-fusion.ts:120）语义正确：λ 越大越准确性。**但 config.ts:15 注释写反**（"越大越强调多样性"）——与 preference.engine.ts:66-73 的权威实现矛盾，维护误导风险。

### 3.3 规则引擎子权重（rule-engine.ts:28-59）

风格 0.3 > 情绪 0.25 > 热度/时段 0.15 > 新鲜度/趋势 0.1，层次合理；缺省值设计（无画像时风格/情绪 0.3、时段 0.5、新鲜度 0.3）使无数据用户不至于得 0 分，但**大量硬编码缺省导致分数区分度塌缩**（见 5.3）。

### 3.4 特征相似度权重（song-feature-extractor.ts:191-196）

声学 0.6 / 语义 0.4——在"真实声学特征"前提下合理（频谱均衡是音乐相似性的强信号），**但当前声学全 0.5 使 0.6 权重退化为常数**。

### 3.5 其他关键参数

| 参数 | 值 | 位置 |
|---|---|---|
| 收藏加分 | +0.3（加在加权融合之后） | recommendation-fusion.ts:16, 87-89 |
| 反馈权重 | dislike 2 / favorite 3 / like 1 | recommendation.controller.ts:34 |
| 候选池 | 2000→过滤→1000 | recommendation.service.ts:157, 166 |
| 协同阈值 | Jaccard >0.05，Top10 相似用户，500 条事件 | collaborative-filter.ts:126, 132, 43 |
| 缓存 TTL | 池 300s / 画像 1h / 相似歌 30min / 特征 24h | recommendation.service.ts:13, config.ts:46-49, song-feature-extractor.ts:35 |
| 热度公式 | 播放 40% + 点赞 20% + 收藏 20% + 评论 10% + 时间衰减 10% | content.service.ts:279-286 |

## 四、数据来源与数据质量（关键事实）

| 数据 | 来源 | 质量评估 |
|---|---|---|
| 声学特征（song_features 8 维） | **种子数据全部为中性占位 0.5**：output/seed-data-new.sql:27198 起共 664 条 INSERT 全部为 `0.5,0.5,0.5,0.5,0.5,0.5,0.5,0.5, bpm=0, energy=0`；Jamendo 导入同样显式写中性 0.5（jamendo.service.ts:255 注释"声学维度先给中性值 0.5"）；全项目**无真实音频特征分析管线**（scripts/ 无 feature 提取脚本，tools-stub 不含） | ❌ **致命**：零方差，见 5.1 |
| 语义标签 | song_genres / song_moods / song_scenes 关联表（ Jamendo 导入时映射；旧曲来自爬虫/种子） | 部分可用，覆盖率未统计 |
| 行为事件 | listening_event，客户端 POST /listening/ingest 上报（listening.controller.ts:5-34） | engagementScore 由**客户端提供**（:32，缺省 0），服务端画像用 `|| 0.3` 兜底（user-profile-builder.ts:114）；feat* 字段对无 songId 事件不可回填 |
| 情绪 DNA | user.emotionDna JSON ← 由事件 feat* 聚合（emotion-dna 模块）；事件特征从 SongFeature 回填（listening.controller.ts:36-61） | **连带退化**：回填源是 0.5 常量 |

| 基因坐标 | PCA(8 维声学)（genome.service.ts:76-105），种子中 genome_x/y = -1/-1 占位 | **退化**：常量输入的 PCA 无意义 |

## 五、当前问题清单

### A. 推荐效果类

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| A1 | **声学特征全库 0.5 常量，无真实特征管线** | seed-data-new.sql:27198+、jamendo.service.ts:255、schema.prisma:447-466 | 内容过滤声学维无判别力（质心恒 0.5，余弦恒 1）；相似歌曲 0.6 声学权重退化为每对相似度 +0.6 常数，排序仅剩 0.4×语义；PCA 基因图/情绪 DNA 连带退化。**当前"内容推荐"实际只依赖语义标签与热度** |
| A2 | **AI 权重与规则引擎信号重复** | rule-engine.ts:29-36 vs ai-enhancer.ts:99-108 | 同一份 favoriteGenres/favoriteMoods 计算两次（比例法 vs 权重占比法），风格/情绪有效权重膨胀，挤占协同/热度多样性 |
| A3 | **收藏歌曲 +0.3 加在归一化融合分之后** | recommendation-fusion.ts:16, 87-89 | ①破坏 0-1 分数尺度（+0.3 ≈ 30% 硬加分）；②把用户**已收藏的已知歌曲**推进每日推荐 Top 榜，信息增益存疑 |
| A4 | **缺省分硬编码过多** | rule-engine.ts:70/86/104/126/131、content-filter.ts:27/33、collaborative-filter.ts:30/69 | 无画像/无相似用户/无特征时大量候选同分 → 排序退化为候选池顺序（= hotScore 降序），个性化失效，仅剩热度推荐 |
| A5 | **协同过滤权重与单用户现实不匹配** | config.ts:40、collaborative-filter.ts:29-31 | 桌面版实际单用户，CF 恒空返 0.3 默认分，0.25 权重无信息量（动态权重逻辑未覆盖此态） |
| A6 | **反馈权重存储但不参与评分** | recommendation.controller.ts:34（dislike 2/favorite 3/like 1）→ 画像只选 weight 字段却不使用（user-profile-builder.ts:52-55） | favorite/like 的强度信息浪费；feedback 仅用于排除与动态权重 |
| A7 | **fallbackHot 过滤标准不一致** | recommendation.service.ts:230-237 | 兜底热歌不经过 isMusicContent 过滤也不要求特征——播客/异常内容可经兜底进入每日推荐 |

## 六、可优化项与优先级

| 优先级 | 优化项 | 理由 | 建议做法 |
|---|---|---|---|
| **P0-1** | **建立真实声学特征管线**（或先用可推导的替代特征） | A1 是全链路效果的天花板：0.5 常量使 content 0.3 权重、相似歌 0.6 声学权重、PCA、情绪 DNA 四条线全部失效。已有 audio-validate/音频解析基础设施可复用 | 用 Web Audio/ffmpeg 对曲库 664 首（158 mp3 本地可及）离线提取 8 维频谱 + bpm/energy，写回 song_features；分批跑、缓存 computedAt |
| **P0-2** | **MMR 性能修复** | B1 直接击穿电台个性化（3s 竞速恒超时）且每日推荐首次生成可能秒级~分钟级阻塞 | ①只对融合分 Top-N（如 50，≈5×daily 推荐数）做 MMR；②相似度回调预构建 Set（在 fuse 中一次性物化 genre/mood Set）；③radio 竞速超时随之自然满足 |
| **P1-1** | 相似歌曲复用 extractBatch | 消除 500 次往返（B2），一行级改动 | similar-song-recommender.ts:57-59 改批量 |
| **P1-2** | AI 权重改独立信号 | 消除 A2 双重计算：ai 槽位改为"探索度/新颖度"（基于 behavior.recentTrend + 候选与历史重叠度），或直接并入 rule 并重新分配权重 | ai-enhancer.score 重写信号源 |
| **P1-3** | 收藏加权重设计 | A3：改为"相似于收藏"而非"收藏本身"——用收藏歌曲特征作为第二质心并入 ContentFilter，去掉 +0.3 硬加分 | fusion 移除 FAVORITE_SCORE_BOOST，content-filter 增加收藏质心 |
| **P1-4** | fallbackHot 统一过滤 | A7：兜底也走 isMusicContent + 优先有特征 | recommendation.service.ts:230-237 复用过滤 |
| **P2-1** | 协同权重自适应单用户态 | A5：相似用户为空时把 collaborative 权重就地重分配给 content/rule（在 fuse 内检测，而非只靠 config 预设） | fusion.fuse 内动态再归一 |
| **P2-2** | 反馈权重参与画像 | A6：favorite/like 加权进 computeFavoriteGenres/Moods | user-profile-builder 消费 weight 字段 |
| **P2-3** | 配置持久化 + MMR 文档修正 | C1/C2：PUT /config 落库（system_config 表），修正 config.ts:15 注释，合并两个 MMR 或重命名区分 | — |
| **P2-4** | 时区显式化（C3）、bpm/energy 字段决策（C4）、AIEnhancer 更名（C5）、quality 指标细化（C6） | 低成本可维护性改进 | — |

## 七、无法确认之处（如实声明）

1. **MMR 实际耗时未实测**：B1 的秒级~分钟级为复杂度推导估算；当前开发/生产实例均未运行，未能对 664 首全量候选做计时验证。
2. **engagementScore 客户端实际取值分布未核实**：web/desktop 前端如何计算该值（上报逻辑）不在本次后端排查范围内；若客户端恒传 0，画像权重将全部走 `|| 0.3` 兜底，进一步均质化。
3. **506 首旧曲的 genres/moods/scenes 覆盖率未统计**：种子 SQL 中存在数据但未做占比分析，影响语义 multi-hot 判别力评估。
4. **真实用户量级与事件分布未知**：影响协同过滤与活跃度评分（activityScore 以"7 天 350 事件封顶"为假设，behavior-analyzer.ts:176-182）的合理性判断。
5. **动态权重阈值（事件<10、dislike>50%）无调参依据记录**：代码与文档中均未找到这些阈值来源，可能为经验值。
6. **种子 0.5 特征的历史成因**：从代码看是"先占位后补真实特征"的中间态（jamendo.service.ts:255 注释），但是否存在已废弃的真实特征管线未能从当前代码树确认（历史提交不在本报告范围）。
